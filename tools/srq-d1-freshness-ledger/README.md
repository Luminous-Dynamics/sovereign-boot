# SRQ D1 freshness ledger (reference implementation)

## Purpose

This dependency-free Rust crate implements one narrow building block for a future D1 path: bind an externally appraised evidence record to a fresh, single-use challenge, and reject replay, expiry, and target/policy/deployment mismatch. The consuming state transition is serialized by a mutex; one correctly bound response marks the challenge consumed atomically.

## Binding contract

A challenge binds the target ID, durable decision ID, expected logical generation, expected immutable deployment ID, effective policy digest, artifact digest, issue time, and exclusive expiry. The response must bind to the same challenge/target/decision/policy/artifact and generation. The observed booted deployment and current userspace deployment are compared independently; a live userspace switch is not accepted as proof of reboot into the authorized generation. The response also carries a measurement-source identifier, observer tool-build SHA-256, appraisal-record SHA-256, verifier ID, and observation time.

- Challenge IDs must be 32 CSPRNG-generated bytes encoded as 64 lowercase hexadecimal characters. This crate validates representation but does not generate randomness.
- The caller supplies a current Unix time and monotonic-nanosecond reading. The monotonic deadline prevents a wall-clock adjustment from extending challenge lifetime.
- Evidence observation time must be inside the issue/expiry window and cannot be later than current wall time.
- A wrong target, decision, generation, deployment, policy or artifact does not consume the challenge; a later correct response can still succeed before expiry.
- A valid response consumes the challenge once. The mutex serializes concurrent consumption.
- Expired and consumed IDs remain retained; capacity exhaustion fails closed rather than evicting replay history.

## Relationship to established systems

The separation follows the role model in [RFC 9334 (RATS)](https://www.rfc-editor.org/rfc/rfc9334.html): an attester supplies Evidence, a verifier appraises it under policy, and a relying party makes the authorization decision. This crate sits after appraisal and handles freshness/binding/replay state only. It does not replace the verifier or the relying party.

The deployment/update safety case must also compose with [TUF](https://github.com/theupdateframework/specification/blob/master/tuf-spec.md), which addresses rollback, freeze and mix-and-match threats in update metadata. A fresh nonce alone does not prove that the image is authorized or recent; signature verification, policy/reference-value authenticity and deployment measurement remain separate gates.

## Explicit non-claims

This is not a complete remote-attestation system or production D1 qualification. The crate does not verify signatures, TPM quotes, certificate chains, measured boot, artifact contents, or verifier policy. The AppraisedEvidence input must come from an independently trusted verifier, and the caller must authenticate that record before using this API. Digest-shaped strings and a verifier ID are identifiers, not cryptographic proof.

Deployment IDs are treated as opaque canonical identifiers here. The observation producer must resolve the booted system and current userspace identity safely and canonically before constructing the signed/appraised response. The ledger does not read host paths or measure the artifact.

The store is volatile, process-local, and not crash durable. Restarting the process loses its replay history. Production use requires a durable transactionally updated store, challenge CSPRNG, protected time source, signed/verified evidence, authenticated verifier policy, key rotation/revocation rules, secure booted-versus-current measurements, and independent review. It does not issue an SRQ release PASS.

## Acceptance criteria

- Exactly one success under 64 concurrent submissions of the same valid response.
- Zero false accepts for replay, wrong decision/generation/deployment, live userspace switch, target/policy/artifact mismatch, malformed digest, expired challenge, time rollback or future timestamp.
- Valid positive control remains accepted after each rejected wrong-binding attempt.
- No custom cryptographic algorithm or random-number generator is included.
- The next qualification tier must add real signature verification, key lifecycle/rotation, durable atomic replay state and fault-injection across process/VM restart before production claims.
